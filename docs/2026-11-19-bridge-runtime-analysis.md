# Figma bridge 무응답·런타임 중단·백그라운드 relay 분석

작성일: 2026-11-19. 대상: `figma-dev-mode-for-free`, 브랜치 `feature/multi-session-figma-bridge`, HEAD `022d8726733b8f72b2ccbaf59767474919f19a33`.

## 결론부터

플러그인 콘솔에서는 **`Error: Plugin runtime aborted`**가 관찰되었지만, 메시지에 타임스탬프가 없어 **발생 시각이 불명이며 11월 17일 장애와 연결할 수 없다.** 11월 17일에 확인된 것은 relay의 즉시 목록 응답과 플러그인 연결 부재다. 콘솔 메시지만으로 Figma 앱 전체 크래시, OS 메모리 부족(OOM), 특정 속성 getter의 결함을 확정할 수 없다.

로컬 코드에서는 다음 세 가지를 확인했다.

1. 페이지 전체 조회는 플러그인에서 동기 재귀 순회·직렬화를 수행한다. 규모가 크면 긴 실행과 메모리 부담이 생길 수 있는 구조다.
2. relay 타임아웃은 응답 대기 항목을 지우고 오류를 돌려줄 뿐, 실행 중인 플러그인 작업을 취소하지 않는다. **MCP 타임아웃과 Figma 작업 종료는 별개**다.
3. MCP 어댑터는 시작 직후 relay 접속을 시도하고, 접속 거절 시 detached relay를 띄운다. relay에는 idle 자동 종료가 없다. 따라서 Figma를 직접 사용하지 않아도 MCP 탐색 과정에서 시작하고 남아 있을 수 있다.

위 1~2는 장애의 유력한 조사 방향이고, 3은 백그라운드 잔존을 설명하는 별도 생명주기 문제다. 관리자 인증창은 과거 진단 중 실행한 `sfltool dumpbtm`과 관련된 사건으로, 동일 원인으로 합치지 않는다.

## 조사 범위와 증거의 등급

- 이번 작업: 저장소 이력·현재 코드·기존 테스트 코드·관련 로컬 로그의 제한된 문자열 검색을 읽고 이 문서만 작성했다.
- 현재 저장소는 조사 시작 시 깨끗했다. 코드·설정·빌드 산출물을 수정하지 않았다.
- 실제 Figma 파일이나 운영 relay에 요청하지 않았다. Figma 재시작, 프로세스 종료, 부하 재현, 관리자 명령, `sfltool` 실행을 하지 않았다.
- 아래 **과거 관찰**은 당시 사용자와 확인한 결과를 요약한 것이며, 이번에 다시 재현하거나 원본 덤프를 재수집했다는 뜻이 아니다.
- **코드 확인**은 위 HEAD의 추적 소스를 기준으로 한다. 디스크의 비추적 dist에도 eager 접속·detached 시작 코드가 있지만, 장애 당시 실행 PID가 정확히 어느 빌드를 로드했는지는 미확정이다.

## 1. 변경 이력과 확인된 동작

### 10월 24일: 다중 세션 격리 구현

`022d872`는 MCP stdio 어댑터마다 대상 선택 상태를 두고, 공용 localhost relay가 플러그인 인스턴스와 요청을 라우팅하도록 바꿨다.

- 요청마다 relay UUID를 발급하고 응답을 보낸 플러그인 소켓까지 확인한다 (`mcp-server/src/bridge.ts:116–156`).
- 연결 교체·끊김 시 해당 pending 요청을 정리한다 (`bridge.ts:69–82,159–188`).
- 선택한 대상이 끊기면 다른 파일로 자동 전환하지 않는다.
- 커밋 메시지에는 당시 14개 테스트 및 두 빌드 통과가 기록되어 있다. **이번 조사에서는 재실행하지 않았다.** 커밋 당시 실제 Figma Desktop/OpenCode 통합은 미검증이라고 명시되어 있었다.
- 10월 26일에는 선택 조회 오류 후 `figma_select_file`로 정상 동작한 관찰이 있었다. 이는 대상 선택 경로의 사용 사례이지 이후 안정성 전체의 증명이 아니다.

### 11월 2일 이후: 무응답 보고

Figma 전체가 멈춘 것처럼 보이는 현상과 에이전트의 “agent died” 보고가 있었다. 이 두 증상을 같은 프로세스의 사망으로 간주하지 않는다. 사용 중인 Figma 플러그인 런타임, Figma 앱, MCP 어댑터, relay, 호출 에이전트는 서로 다른 실패 지점이다.

### 11월 7일: 자동 시작과 인증창 조사

- 직접적인 relay 로그인 항목·백그라운드 등록은 당시 조사 범위에서 찾지 못했다. FigmaAgent는 별개였고 ChatGPT/Codex 로그인 항목은 꺼져 있었다.
- relay 시작은 10:44:42 KST, Agent Cat helper 시도는 10:52:27이었다. 뒤의 시도로 앞의 시작을 설명할 수 없다. 해당 앱의 정확한 시작 시각·최초 생성자는 확정되지 않았다.
- 관리자 인증창은 조사 중 `sfltool dumpbtm` 실행 자체에서 발생한 것으로 구분했다. relay가 관리자 권한을 요구했다는 증거로 사용하지 않는다.

### 11월 10일 KST: 재부팅 후 순서

당시 확인 순서는 재부팅 00:16:06 → Agent Cat/CodexBar 자동 시작 00:16:41 → ChatGPT 00:19:37 → MCP 카탈로그 00:19:44–49 → relay 00:19:47 → ChatGPT 자식 app-server 연결 00:19:53/55였다. relay는 진단 시작 전 이미 떠 있었다. 최초 생성 PID는 복구하지 못했다.

이 순서는 **MCP 초기화가 relay를 띄울 수 있다는 코드와 부합**하지만 특정 앱을 단독 원인으로 확정하지는 못한다. idle CPU 세 표본은 0%, 연결 클라이언트 없음, 관련 프로세스 합산 RSS 약 105 MiB였다. 이전 54 MiB 수치와는 집계 범위가 달랐다. 단기 idle 측정은 장시간 누수·부하 시 안정성을 증명하지 않는다.

lazy 시작과 idle 종료는 당시 제안이었으며 현재 HEAD에도 구현되어 있지 않다.

### 11월 16~17일: 서로 구분해야 할 관찰

- 11월 16일 사용자는 MCP 타임아웃 뒤 Figma가 멈췄다가 회복하는 현상을 관찰했다. 당시 실행 코드 버전과 실제 요청의 depth·detail은 확인되지 않았다.
- 11월 17일 장애 당시 읽기 전용 상태 확인에서 relay는 대상 목록에 즉시 응답했고, Figma 플러그인 연결 0개·에이전트 연결 4개였다. 그 순간 relay 이벤트 루프가 완전히 멈춘 상태라는 가설에는 반대 증거다. 이전 순간의 지연이나 다른 장애까지 배제하지는 않는다.
- 당시 relay 출력은 버려지고 있었고, 검사한 범위에서 Figma 앱 크래시 보고서는 발견되지 않았다.
### 시각 불명: 플러그인 콘솔의 중단 메시지

사용자가 연 플러그인 콘솔에 다음 메시지가 보였다. **메시지에 타임스탬프가 없었으므로 11월 17일 장애 당시 발생한 것으로 기록하지 않는다.**

  ```text
  Memory leak: 29003768 bytes lost in 3625502 blocks
  Error: Plugin runtime aborted
  ```

  스택에는 노드 속성 읽기가 있었고, 동기화되지 않은 변경 경고도 관찰했다. 이는 **발생 시각을 알 수 없는 플러그인 런타임 중단 메시지의 관찰**이다. 11월 16일 멈춤이나 11월 17일 연결 부재와 같은 사건인지 미확정이다. leak 메시지는 런타임 정리 과정의 진단일 수 있으며 원인이라고 볼 수 없다. 집계 숫자나 스택만으로 실제 원인·OS OOM·Figma 앱 프로세스 사망·특정 getter 결함을 단정하지 않는다.

## 2. 현재 코드로 설명되는 부분

### 2.1 시작 및 잔존

`mcp-server/src/index.ts:810–814`의 main은 stdio 서버 연결 직후 `bridge.listTargets()`를 호출한다. 명시적인 Figma 도구 호출 전에도 relay 연결이 일어난다.

`bridge.ts:287–304`는 ECONNREFUSED일 때 relay를 시작하고 최대 8초 동안 재접속한다. `bridge.ts:217–228`은 detached, stdio ignore, unref 방식으로 자식 프로세스를 분리한다. `startBridgeServer`와 연결 종료 처리에는 idle 종료 타이머가 없다. 기존 테스트에도 첫 어댑터 종료 후 relay가 살아서 다음 어댑터를 받는 시나리오가 있다.

따라서 프로세스 잔존은 현재 설계와 일치한다. 이는 로그인 항목 등록이나 악성 실행의 증거가 아니다. stdio ignore 때문에 시작 실패·요청 시점의 인과관계를 나중에 추적하기 어려운 점은 별도의 관측성 결함이다.

### 2.2 타임아웃은 취소가 아니다

- 일반 조회는 30초, 전체 페이지 조회는 120초 (`index.ts:350–386`).
- relay는 시간 초과 시 pending을 삭제하고 요청자에게 오류를 보낸다 (`bridge.ts:129–137`).
- 클라이언트는 relay보다 2초 더 기다리는 타이머를 갖는다 (`bridge.ts:260–268`).
- 이 경로에는 downstream cancel 명령이나 플러그인 작업의 협력적 취소 확인이 없다.
- 뒤늦은 응답은 이미 pending이 없으면 무시된다 (`bridge.ts:146–150`).

따라서 타임아웃 직후 같은 무거운 요청을 재시도하면 앞 작업이 끝났다는 보장 없이 추가 작업을 보낼 수 있다. 실제 사건에서 요청이 몇 번 겹쳤는지는 당시 파라미터·요청 ID 기록이 없어 미확정이다.

### 2.3 전체 페이지 동기 직렬화

`src/code.ts:358–515`의 `serializeNode`는 자식들을 동기 재귀 map으로 순회한다. `get_page_full`은 기본 maxDepth 100, forceDetail=true로 상세 축소를 우회한다 (`src/code.ts:592–607`). 페이지 전체 응답을 만든 뒤 어댑터가 통계·JSON 파일을 작성한다 (`index.ts:378` 이후).

로컬 파일로 저장해 최종 MCP 응답을 줄여도, **Figma 내부에서 큰 트리를 만드는 비용과 플러그인→UI→relay 전송 비용은 사라지지 않는다.** 노드 수·텍스트 상세·메모리 사용·한 번에 처리하는 요청 수에 대한 실측이 필요하다. 현재 경로에는 작업량 기반 분할/yield나 취소 플래그가 보이지 않는다.

### 2.4 maxDepth=0 처리

`index.ts:352,363`의 `Number(args.maxDepth) || 5`, 372의 `... || 3`은 입력 0을 기본값으로 바꾼다. 즉 호출자가 depth 0으로 범위를 줄이려 해도 기대보다 깊게 읽을 수 있다. 전체 페이지 경로는 0을 100으로 바꾸며 이후 허용 범위도 1 이상이다.

이 동작은 소스에서 확인한 입력 처리 문제다. **장애 요청이 실제로 0을 사용했다거나 이 문제 때문에 중단되었다고 확정하지 않는다.** 전체 페이지의 0 허용 여부는 API 계약부터 정해야 한다.

## 3. 남은 가설과 필요한 증거

| 가설 | 현재 근거 | 부족한 증거 |
| --- | --- | --- |
| 대규모 직렬화·속성 읽기가 플러그인 런타임에 과부하를 줌 | 동기 순회·full detail이라는 코드 구조. 시각 불명의 콘솔 중단·속성 읽기 스택은 별도 관찰 | 콘솔 시각과 장애의 연관성, 실제 호출 도구/파라미터, 노드 수, 빌드 식별자, 재현 최소 파일, 시간별 메모리 |
| 타임아웃 후 재요청이 부담을 겹치게 함 | 취소 프로토콜 없음 | 당시 요청 ID별 시작·완료·타임아웃 순서 |
| relay 전체 정지가 주된 원인 | 처음의 사용자 체감만으로는 가능 | 11/17 즉시 목록 응답은 이 가설을 약화. 당시 CPU/지연 추이 필요 |
| 프로세스 자동 시작은 MCP 카탈로그/초기화에 기인 | eager 접속 코드와 11/10 시각 부합 | 최초 spawn 부모 PID·생성 이벤트 연결 |
| 관리자 인증창과 무응답이 같은 장애 | 현재 연결 근거 없음 | 별도 사건으로 유지해야 함 |

## 4. 안전한 다음 진단·개선 순서 (아직 미실행)

1. 동기화되지 않은 변경이 있으면 먼저 사용자가 Figma 동기화 상태와 복사본을 확보한다. 원본 대형 파일로 반복 부하 재현하지 않는다.
2. 다음 장애는 도구명, 파라미터의 크기·깊이·detail, 요청 ID, 빌드 커밋, 시간만 먼저 기록한다. 토큰·파일 키·개인 디자인 본문은 로그에 남기지 않는다.
3. 별도 작은 테스트 파일에서 파일 정보 → 단일 선택 minimal/depth 낮음 → 단계적 노드 증가로 비교한다. 타임아웃 시 즉시 중단하고 재시도 누적을 피한다. full page는 마지막 단계로 남긴다.
4. 독립 테스트 포트·가짜 플러그인에서 timeout 후 pending 정리, 늦은 응답, 취소 전달 계약을 검증한다. 운영 3055에 테스트를 섞지 않는다.
5. 개선 후보: 요청 큐/동시 실행 상한, 노드·바이트 예산, 점진적 순회와 yield, 협력적 취소, 최소 수집 후 필요한 노드만 상세화. 타임아웃 숫자만 늘리는 것은 작업 취소나 메모리 절약이 아니다.
6. maxDepth 기본값 처리는 0의 의미를 명시하고 누락·0·음수·NaN·상한 테스트로 고정한다.
7. relay 생명주기는 별도 변경으로 다룬다. 실제 도구 사용 시 lazy 접속, 모든 클라이언트·pending이 없는 경우의 유예 종료를 검토하되 재연결 경합과 다중 어댑터 테스트를 추가한다. 아직 구현된 것으로 설명하지 않는다.
8. 프로세스 시작 원인 추적은 권한 상승 없는 시작 시각·부모 PID·종료 원인 등 제한된 메타데이터로 진행한다. 진단이 프로세스를 새로 띄웠는지도 구분한다. 관리자 인증창을 유발했던 명령을 무심코 재사용하지 않는다.

## 5. 이번 검증 및 한계

- 현재 코드의 eager 초기 접속, detached 잔존, timeout 후 미취소, 동기 full traversal, depth 0 기본값 치환을 읽어서 확인했다.
- Mac의 11월 Codex 데스크톱 로그를 해당 오류 문자열로 제한 검색했지만 `Plugin runtime aborted`, 위 leak 숫자, `agent died`의 원본 로그는 찾지 못했다. 사용자 플러그인 콘솔 관찰을 대신 부정하거나 확증하는 결과는 아니다. 관련 bridge 문자열은 있었으나 개별 생성자의 인과관계 복구에는 사용하지 않았다.
- 검사한 DiagnosticReports 파일명 범위에서 Figma 관련 보고서를 찾지 못했다. 보관·권한·수집 범위 밖 보고서가 없다는 뜻은 아니다.
- 과거 테스트 통과 이력은 현재 실제 Figma에서의 재현 테스트와 다르다. 이번에는 테스트 실행·빌드·운영 상태 탐침을 하지 않았다.
- 이 문서 외 파일을 변경하지 않았고 git pull·commit·push 및 런타임 설정 변경을 하지 않았다.
